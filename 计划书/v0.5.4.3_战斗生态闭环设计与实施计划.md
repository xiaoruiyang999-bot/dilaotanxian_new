# v0.5.4.3 战斗生态闭环：设计与实施计划

> 本版本闭环完成后的体验优化由 [`v0.5.4.4_远程AI与战斗平衡设计计划.md`](./v0.5.4.4_远程AI与战斗平衡设计计划.md) 接续，重点为 LOS、方向预警、距离滞回、墙边选位与动态遭遇难度。

## 1. 版本目标

本版本不以“再增加一种敌人”为目标，而是让现有 Melee、Ranged、Skirmisher、Charger、Summoner 形成可运行、可组合、可扩展、可验收的战斗生态。

完成定义：

1. 五种基础敌人的核心攻击均可实际运行，不存在空 Prefab 引用。
2. 房间不再只按数量随机，而是按预算、职责和同类上限生成合理组合。
3. 敌人死亡、召唤物、清房和开门形成完整生命周期闭环。
4. 精英变化通过可配置 Modifier/Affix 叠加，不复制整套 AI 代码。
5. 所有阶段必须先通过隔离测试，再进入完整地牢 Play Mode 验收。

## 2. 范围与非目标

### 本版本范围

- Ranged 投射物发射、命中、撞墙与生命周期。
- Summoner 的 Minion 资源、数量上限、死亡追踪与清房计数。
- Encounter Budget 遭遇编排。
- 敌人职责、成本和单房间数量上限。
- 精英词缀的最小可扩展框架。
- 死亡、房间清理和门状态回归测试。
- 配置校验、运行时保护及配套文档。

### 暂不纳入

- Boss 多阶段演出与完整招式树。
- 玩家装备、局外成长和复杂掉落系统。
- 联机同步。
- Addressables 远程资源加载。
- DOTS/ECS 重构。

## 3. 总体架构

```text
表现层
├─ Projectile / AttackIndicator / Renderer / Trail
│
战斗执行层
├─ EnemyAI：决策、距离控制、职责行为
├─ EnemyCombat：攻击状态机与特殊攻击执行
├─ EnemyController：移动、死亡退出和物理控制
└─ EnemyHealth：生命与死亡事件
│
遭遇编排层
├─ EnemySpawner：执行生成并注入随机源
├─ SpawnTable：候选、权重、成本、职责、同类上限
└─ Encounter Budget：根据预算构建敌人组合
│
房间生命周期层
├─ Room：敌人注册、死亡核对、Cleared 状态
└─ Door：根据相邻 Room 状态刷新碰撞和视觉
│
数据层
├─ AttackData：攻击参数和 Projectile/Minion 引用
├─ EnemyBehaviorConfig：行为偏好
├─ SpawnTable：遭遇配置
└─ EnemyAffixConfig（计划新增）：精英修饰配置
```

### 依赖方向

- 数据层不引用场景对象。
- AI 只发出决策，不直接生成房门或修改房间状态。
- Combat 只执行攻击，不决定房间是否清除。
- Room 只依赖 `EnemyHealth` 生命周期，不识别具体敌人类型。
- Spawner 负责创建和注册，不接管敌人运行状态机。
- Door 不保存独立战斗状态，只从相邻 Room 推导开关。

## 4. 预使用技术与选择理由

| 技术 | 用途 | 选择理由 | 暂不使用的替代方案 |
|---|---|---|---|
| ScriptableObject | AttackData、BehaviorConfig、SpawnTable、Affix 配置 | 现有项目已经采用；Inspector 可调且无需改 AI 代码 | JSON 配置会增加导入和引用维护成本 |
| Prefab Variant | Ranged/Skirmisher/Charger/Summoner/Minion | 共享基础敌人生命周期，避免组件漂移 | 完全独立 Prefab 容易漏同步修复 |
| `System.Random` 子 seed | 遭遇组合与招式选择 | 保持同 seed 可复现，便于测试 | `UnityEngine.Random` 全局状态难以隔离 |
| Rigidbody2D + Trigger | 投射物和伤害碰撞 | 与现有 2D 物理体系一致 | 手写空间查询不适合当前规模 |
| LayerMask | 目标和障碍物过滤 | 低成本、Inspector 可配置 | Tag 不能有效表示复合碰撞类别 |
| 事件 + 主动核对 | 敌人死亡与清房 | 事件保证及时，主动核对防止遗漏导致永久关门 | 只依赖事件已被证明不够稳健 |
| 预算式生成 | 控制战斗组合强度 | 比单纯数量随机更可控，可自然连接楼层难度 | 纯随机权重容易产生全后排等坏组合 |
| Unity MCP 隔离测试 | Prefab、状态机、销毁、资源引用验证 | 能直接验证真实 AssetDatabase 与 Play Mode | 只做文本/YAML 检查无法证明运行行为 |

### 对象池决策

当前版本先保留 Projectile 的 Instantiate/Destroy，以正确性优先。满足下列任一条件后再引入通用对象池：

- 同屏投射物稳定超过 30 个；
- Profiler 显示投射物创建/回收造成可见 GC 峰值；
- 加入三连发、弹幕或 Boss 高频远程招式。

对象池不得与本版本的远程正确性修复绑在同一个提交阶段，避免生命周期问题互相掩盖。

## 5. 数据模型

### AttackData

- `isProjectile` 与 `projectilePrefab` 必须成对有效。
- `isSummon` 与 `summonPrefab` 必须成对有效。
- Projectile 使用 `targetLayer` 和 `obstacleLayer`。
- Charger 使用 `chargerCollisionLayer`，不与 Projectile 的 `obstacleLayer` 混用。

### SpawnTable.Entry

- `weight`：同等条件下的抽取权重。
- `minCount`：硬性保底数量。
- `encounterCost`：占用的战斗预算。
- `maxPerRoom`：同一房间上限，0 表示不限。
- `role`：`Frontline / Ranged / Flanker / Support`。

### Combat 房默认预算

| 敌人 | Role | Cost | Max/Room | Weight |
|---|---:|---:|---:|---:|
| Melee | Frontline | 2 | 不限 | 10 |
| Ranged | Ranged | 2 | 2 | 6 |
| Skirmisher | Flanker | 2 | 2 | 6 |
| Charger | Frontline | 3 | 2 | 4 |
| Summoner | Support | 4 | 1 | 3 |

Combat 房预算暂定 `5–9`，并要求至少一个 Frontline。预算不足、候选无效或达到上限时必须安全停止，不允许死循环。

## 6. 分阶段实施

### 阶段 A：远程与召唤闭环（已完成）

交付：

- 创建 `Enemy_Minion.prefab` Variant。
- 绑定 `AttackData_Ranged.projectilePrefab`。
- 绑定 `AttackData_Summoner.summonPrefab`。
- 验证 Projectile 命中玩家一次、撞墙销毁、超时销毁、不命中发射者。
- 验证 Summoner 不超过 `maxMinionsAlive`，Minion 计入清房。

退出条件：所有资源引用非空，Unity 0 Error，隔离测试通过。

验证结果（2026-08-14）：

- Ranged 的 Projectile 引用有效，隔离测试单次命中正确扣除 1 点生命。
- Projectile 障碍物 Layer 分支已触发，撞墙进入销毁流程。
- Summoner 的 Minion 引用有效；连续召唤严格限制为 4 只。
- 先杀 Summoner 时 Room 保持 Active；杀死全部 Minion 后 Room 切换 Cleared。
- Unity Console：0 Error。

### 阶段 B：遭遇编排（已完成）

交付：

- SpawnTable 支持预算、职责、成本和同类上限。
- EnemySpawner 在预算关闭时保持旧逻辑兼容。
- Combat 表启用 `5–9` 预算并保证前排。
- 同 seed 的组合结果可复现。

退出条件：至少 500 次纯逻辑抽样无“缺少前排”、Summoner 超限或死循环。

验证结果（2026-08-14）：

- 500 次预算抽样 0 失败，组合数量范围 2–4，出现过 Ranged 与 Support。
- 200 个 seed 分别重复构建两次，组合结果完全一致。
- 完整地牢生成 6 个战斗类房间，0 个空房、Combat 无前排或 Summoner 超限案例。
- Unity Console：0 Error / 0 Warning。

### 阶段 C：精英词缀最小框架（已完成）

交付：

- 新增 `EnemyAffixConfig`，先支持生命、移动速度、体型、颜色四类非侵入修饰。
- 新增运行时 `EnemyAffix` 应用器；不得复制 EnemyAI/EnemyCombat。
- 词缀由生成层按概率或房间类型注入。
- 首批只提供 `Swift` 与 `Tough` 两个配置，暂不加入死亡爆炸等新攻击机制。

退出条件：普通敌人不受影响；同一 Prefab 可在运行时得到不同修饰；死亡与清房逻辑保持通过。

验证结果（2026-08-14）：

- 新增 `EnemyAffixConfig` 和运行时 `EnemyAffix`，未复制 AI/Combat。
- Swift：移速 ×1.35、体型 ×0.9；Tough：生命 ×1.75、移速 ×0.85、体型 ×1.15。
- 普通敌人数值保持不变；Tough 的当前生命与最大生命同步更新。
- 两种词缀敌人的死亡退出流程通过。

### 阶段 D：完整地牢验收（已完成自动化部分）

交付：

- 连续生成多个 Combat 房并实际战斗。
- 验证五类敌人至少各出现一次。
- 验证全灭开门、召唤物清房、连续重建地牢。
- 记录 Console、房间数量、组合和失败案例。

验证结果（2026-08-14）：

- 完整地牢生成 6 个战斗类房间、17 个敌人，其中 2 个带词缀。
- 实际生成集合包含 Melee、Ranged、Skirmisher、Charger、Summoner 五种敌人。
- 自动清理 6 个战斗类房间，Cleared 失败数为 0。
- 全部房间清除后检查 9 扇门，仍启用的门碰撞体数量为 0。
- Unity Console：0 Error / 0 Warning。
- 人工操作手感（WASD、躲避弹道、敌人组合节奏）仍属于体验验收，不影响代码闭环结论。

## 7. 测试矩阵

| 测试 | 预期 |
|---|---|
| Ranged 发射 | 生成 Projectile，方向和速度正确 |
| Projectile 命中 | 单次伤害后销毁，不重复伤害 |
| Projectile 撞墙 | 不穿墙，立即销毁 |
| Summoner 连续施法 | 活体 Minion 不超过上限 |
| 先杀 Summoner | Minion 存活时房间仍为 Active |
| 杀死全部 Minion | Room 切换 Cleared，门重新打开 |
| Variant 死亡 | AI/Combat/Collider/Renderer 当帧关闭，后续帧对象为 0 |
| 预算抽样 500 次 | 每组至少一名前排，Summoner 不超过 1 |
| 固定 seed | 多次运行获得相同组合 |
| 旧 SpawnTable | 未启用预算时结果仍由 countMin/countMax 控制 |
| 连续 Generate | 旧 Collider 不干扰新地牢 |

## 8. 失败保护与可观测性

- 特殊攻击资源为空时记录一次明确 Warning，并跳过攻击，不抛异常。
- Spawner 遇到无可负担候选时结束本轮，不尝试无限重抽。
- 房间使用死亡事件和 Active 主动核对双通道清理。
- 所有运行时测试结束后退出 Play Mode，不把测试对象写入场景。
- 调试日志只保留生成摘要和配置错误，不恢复高频伤害/UI 日志。

## 10. 变更纪律

1. 严格按 A → B → C → D 顺序推进。
2. 每个阶段完成后先更新本文档状态，再进入下一阶段。
3. 不在修复 Projectile 时顺便引入对象池。
4. 不通过复制 Prefab 或 AI 类实现词缀。
5. 任一阶段出现 Console Error，立即停止后续扩展并先修复。
